# v0.1.4 Next Feature Line

`v0.1.4` is the next feature development line after `v0.1.3rc2` maintenance
items are triaged. It should improve real user workflows while preserving the
preview-first safety boundaries established in v0.1.

OpenSolver Workbench remains educational/research software. It is not a stable
production or industrial-certified solver platform. Users must validate
engineering results independently.

## Purpose

- Start the next feature development cycle after maintenance triage.
- Improve onboarding and tutorial paths for source installs and portable use.
- Make project, plugin, result, field, and report workflows easier to inspect.
- Plan optional solver validation dashboards without making optional solvers
  mandatory.

## Candidate Themes

| Theme | Candidate direction | Guardrail |
| --- | --- | --- |
| Onboarding tutorials | Add task-oriented tutorials for demo project, plugin health, report summary, and result inspection. | Use existing fixtures and avoid commercial software. |
| Project workflow polish | Improve project validation messages, navigation, and common CLI/GUI handoffs. | Keep mutation previewable and explicit. |
| Plugin manager UX | Improve install receipts, rejection messages, local ZIP/folder diagnostics, and trust wording. | No remote plugin marketplace or dependency auto-install unless separately scoped. |
| ResultViewer workflow | Improve table, figure, and catalog navigation for ResultDataset objects. | Keep heavy visualization dependencies optional. |
| FieldViewer workflow | Improve field metadata display and safe rendering diagnostics. | No full solver field parser claim without explicit parser evidence. |
| Report/export quality | Improve report sections, warnings, and reproducibility notes. | Reports must not execute solvers, scripts, or hidden side effects. |
| Optional solver validation dashboard | Summarize installed/missing/pass/fail optional dependency evidence. | Dashboard is evidence display, not certification. |
| VFEA planning | Consider experimental VFEA planning only if explicitly scoped later. | Planning only; no implicit solver accuracy or production claim. |

## Non-Goals

- No MATLAB, ANSYS, or Simulink clone.
- No industrial certification or compliance claim.
- No commercial native CAD direct import.
- No unreviewed automatic execution of scripts or solvers.
- No full OpenFOAM UI or broad solver coverage.
- No mandatory heavy dependencies for base import, CLI smoke, or unit tests.

## Start Criteria

- `v0.1.3rc2` maintenance tasks are triaged.
- Release asset smoke and public-release checklists have owners or issues.
- Live optional validation targets have a documented evidence plan.
- GitHub milestones and issues exist for the selected feature themes.

## FEASpec IR Design Follow-Up

[FEASpec IR design](../experimental/feaspec_ir_design.md) records the first
post-release experimental design follow-up after VFEA scope closure. It defines
`FEASpecCandidate` versus approved FEASpec, source, units, geometry graph,
materials/sections, boundary conditions, loads, dimensions, assumptions,
evidence/confidence, diagnostics, validation states, solver compatibility,
serialization examples, and future conversion boundaries.

This is design-only evidence. It does not implement FEASpec or VFEA, does not
add VLM APIs or credentials, does not execute solvers, does not make Abaqus
mandatory, and does not change the public `v0.1.4-rc1` release.

[FEASpec examples](../experimental/feaspec_examples.md) and
[FEASpec benchmark seeds](../experimental/feaspec_benchmark_seeds.md) add
canonical JSON examples and synthetic seed fixtures for future implementation
work. They demonstrate candidate, approved, and invalid diagnostic cases with
explicit units, evidence/confidence, validation states, and planned metrics.
They are not generated solver outputs and do not imply VLM benchmark scores.

[FEASpec Python models](../experimental/feaspec_python_models.md) adds the
first experimental post-release model layer for those examples and benchmark
seeds. It can load, basic-check, and serialize FEASpec documents, but it is not
a production/full physics validator, full ProjectSchema persistence,
ProjectSchema mutation, solver adapter, VLM integration, VFEA implementation,
or solver execution path.

[FEASpec validator design](../experimental/feaspec_validator_design.md) records
the future validator contract for that model layer: pipeline phases,
diagnostic schema, severity taxonomy, required diagnostic codes, approval
rules, solver handoff gates, CalculiX-first compatibility, Abaqus
optional/non-default handling, and benchmark readiness. It is design-only and
does not add production validator code, source solver behavior, VLM APIs,
credentials, full ProjectSchema persistence, ProjectSchema mutation, solver
adapters, or release mutation.

[FEASpec validator implementation](../experimental/feaspec_validator_implementation.md)
adds the first experimental semantic validator report layer after the design
gate. It exposes `validate_feaspec`, `validate_for_solver`,
`validate_benchmark_seed`, and `explain_diagnostics`, with structured
diagnostic severities, categories, codes, phase results, solver handoff flags,
CalculiX-first field-level compatibility, Abaqus optional/non-default
diagnostics, and benchmark readiness checks. It remains post-release
development on `develop` and does not implement VFEA, full ProjectSchema
persistence, ProjectSchema mutation, solver adapters/exporters, VLM APIs, mesh
generation, numerical physics validation, solver execution, release mutation,
or asset changes.

[FEASpec to ProjectSchema bridge design](../experimental/feaspec_to_projectschema_bridge_design.md)
records the post-release bridge boundary. The follow-up
[FEASpec to ProjectSchema bridge implementation](../experimental/feaspec_to_projectschema_bridge_implementation.md)
adds an experimental draft-plan layer that requires an approved FEASpec and a
validator report with no blockers, defines field mappings and bridge
diagnostics, preserves provenance/evidence and unmapped fields, and keeps full
ProjectSchema persistence, ProjectSchema mutation, SolverAdapter/export
handoff, VLM APIs, credentials, and solver execution out of scope.

[FEASpec to CalculiX case planning](../experimental/feaspec_to_calculix_case_planning.md)
records the design-only CalculiX-first boundary after bridge planning. It
defines preconditions, a future case-plan object, mesh and element strategy,
material/section, boundary/load, step/output, diagnostics, and issue `#8`
separation without adding a case generator, `.inp` writer, SolverAdapter call,
runner call, live `ccx` validation, or solver execution.

[FEASpec to CalculiX case-plan model](../experimental/feaspec_to_calculix_case_plan_model.md)
adds the bounded experimental planning object after that design gate. It maps
approved FEASpec bridge plans into serializable CalculiX planning records,
preserves diagnostics and provenance, reports `FC_MESH_REQUIRED` until explicit
mesh topology exists, and keeps writer/export/execution behavior outside this
gate.

[FEASpec to CalculiX INP writer design](../experimental/feaspec_to_calculix_inp_writer_design.md)
records the next design-only boundary. It defines the future no-run `.inp`
renderer contract, preconditions, proposed API, result objects, deterministic
file-section ordering, `FW_*` diagnostics, golden fixture strategy, and issue
`#8` separation. It does not implement a writer, generate `.inp` files, call
SolverAdapter or runner code, run `ccx`, mutate ProjectSchema, add VLM APIs, or
change the public release.
