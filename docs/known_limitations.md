# Known Limitations

OSW v0.1 is an educational and research workbench. These limitations are design
boundaries for the v0.1 release, not missing marketing claims. They keep the
demo path inspectable:

```text
Import -> Configure -> Run or prepare -> Result -> Report
```

## Engineering Use

- OSW v0.1 is not industrial certified and does not make certification,
  compliance, warranty, production accuracy, or suitability claims.
- OSW v0.1 does not replace expert engineering judgment, independent review,
  code checks, test evidence, or applicable domain standards.
- Validation examples are educational checks. They document assumptions,
  tolerances, and gaps; they do not establish general-purpose CAE or CFD
  accuracy.
- Reports generated by OSW should be read as reproducibility records for the
  current demo inputs, not as approval for manufacturing, construction,
  operation, or safety decisions.

## Geometry And CAD

- OSW v0.1 supports standard/exported geometry preview workflows such as STEP,
  STL, OBJ, IGES, and BREP stubs where the local optional bridge permits.
- OSW v0.1 does not support commercial native CAD direct import. Export STEP,
  STL, or another supported standard/exported format from the source CAD tool.
- OSW v0.1 does not support direct native import for SolidWorks, CATIA, NX,
  Creo, or comparable proprietary CAD files.
- STEP, IGES, and BREP support is preview-oriented unless a reviewed optional
  CAD kernel is available. Complex healing, feature history, constraints, and
  parametric modeling are outside the v0.1 scope.

## Mesh And Visualization

- Mesh import is limited to standard/exported mesh formats supported by the
  local optional mesh stack.
- Mesh quality metrics are lightweight summaries for review and reporting. They
  do not replace solver-specific mesh convergence studies or formal verification.
- PyVista and Matplotlib integrations are optional visualization surfaces. If
  those dependencies are missing, OSW should report the missing optional module
  rather than making visualization mandatory for base use.

## Solver Workflows

- The GUI does not directly run external solver subprocesses. Solver execution,
  when available, belongs behind reviewed backend runner boundaries with
  explicit working directories, timeout handling, log capture, and artifact
  classification.
- External solver executables such as `ccx`, OpenFOAM tools, SU2, Gmsh, or GNU
  Octave are optional local dependencies. Missing executables should produce
  diagnostics, not import-time failures.
- OSW v0.1 does not bundle external solver installers or commercial solver
  runtimes.

## CalculiX

- CalculiX support is limited to a small linear static educational handoff:
  isotropic elastic material, fixed support, force or pressure load, input deck
  generation, optional runner diagnostics, and basic result summaries.
- OSW v0.1 does not support nonlinear contact, plasticity, broad element
  coverage, advanced load steps, production structural validation, or industrial
  certification claims.
- Cantilever validation helpers are benchmark-style checks with documented
  assumptions and tolerances.

## OpenFOAM

- OpenFOAM support is template-based for bounded cavity and duct examples.
- OSW v0.1 does not provide a full OpenFOAM solver UI, general case editor,
  turbulence advisor, multiphase flow workflow, reacting flow workflow, or broad
  solver coverage.
- Generated OpenFOAM case files are teaching artifacts. Users who run them
  outside OSW must review local OpenFOAM version, boundary conditions, numerical
  schemes, and mesh suitability.

## Chemistry And Property Examples

- Cantera support is limited to bounded 0D reactor examples with explicit SI
  inputs, species/time tables, and reportable diagnostics.
- CoolProp support is limited to property points, small sweep tables, CSV export,
  and plot/report placeholders.
- OSW v0.1 does not provide a process flowsheet simulator, combustion CFD
  solver, reactor network design tool, or proprietary property package bridge.
- Cantera and CoolProp are optional dependencies. Missing packages or missing
  mechanisms/fluids must be reported clearly.

## MATLAB, Octave, And Script Data

- `.m` and `.mat` workflows are preview-first. Importing a script or data file
  must not execute arbitrary code.
- OSW v0.1 does not support Simulink, `.slx`, or `.mlapp` workflows.
- OSW v0.1 does not support full MATLAB proprietary toolbox compatibility.
- GNU Octave execution, when used, must be explicit and routed through the
  reviewed runner path with timeout, stdout/stderr capture, temporary workspace
  handling, and artifact classification.
- `.m` safety scanning is heuristic. It surfaces risky shell, network, file
  mutation, and subprocess patterns, but it does not prove a script is safe.
  Treat script output as untrusted until reviewed and accepted.

## Optional Dependency Behavior

- Base OSW import, CLI smoke, and unit tests should not require PySide6, meshio,
  Gmsh, PyVista, Cantera, CoolProp, GNU Octave, external solver executables, or
  commercial software.
- Optional integrations should use guarded imports and user-readable diagnostics
  when a local dependency is absent.
- Missing optional dependencies can be valid tutorial outcomes when the workflow
  is documenting dependency status rather than executing the optional tool.

## Reporting And Validation

- **Native report-asset availability resolution is unsupported (`DEFERRED_RETAINED`).** OSW can preserve and lexically validate a typed path reference without accessing the filesystem, but it cannot establish existence, regular-file status, readability, locality, containment, link/reparse safety, provider silence, sandboxing, or race-free consumption. Typed unresolved references remain visible as placeholders and can be explicitly relinked. This limitation does not mean the referenced asset is missing, unreadable, unsafe, or nonexistent. Legacy compatibility behavior is separate and is not certified provider-silent.
- **Legacy compatibility paths are outside the typed-resolver `DEFERRED_RETAINED` native policy and are not certified provider-silent.** Their existing path checks or relink behavior may access the filesystem; lexical handling in the typed contract does not convert that behavior into proved filesystem facts. The absence of a new typed native resolver neither validates nor expands legacy behavior, and “unsupported” does not mean a legacy target is missing, unreadable, unsafe, or nonexistent. This closure neither removes nor expands legacy behavior. Any legacy-path security review requires its own authorized gate; explicit relink and unresolved-placeholder behavior remain available within their existing boundaries.
- HTML reports summarize inputs, assumptions, units, warnings, result tables,
  figures, validation notes, and known limitations for the selected demo.
- Report output does not certify a design or replace independent verification.
- Any result without validation evidence should remain marked as preview,
  template, fixture-backed, or educational as appropriate.
